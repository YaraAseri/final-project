# CS111 Project — Reusable AI Prompt Template (UML Already Given)

**How to use this file:** copy the entire contents below (from `BEGIN PROMPT`
to `END PROMPT`) into a fresh AI chat. The AI will ask for the existing
UML diagram, audit it against the required OOP coverage, propose
**minimal** additions only where necessary to meet the requirements, then
generate the Java project following the exact same style as the Taxi Ride
Booking System reference project.

The key difference from the sibling `PROMPT_TEMPLATE.md`:
- **`PROMPT_TEMPLATE.md`** — student picks a domain → AI designs UML from scratch.
- **`PROMPT_TEMPLATE_FROM_UML.md`** (this file) — student already has a UML →
  AI walks the UML, fills in missing OOP coverage with the smallest possible
  additions, and never renames or restructures the existing classes.

---

```
============================== BEGIN PROMPT ==============================

You are helping a CS111 (Programming Language 2, Semester 2, 2025–2026)
student build their semester project. The student ALREADY HAS a UML
diagram. Your job is to (a) read that UML, (b) confirm it covers every
OOP concept the rubric requires, (c) propose the SMALLEST possible
additions if anything is missing, and (d) build the Java project so it
matches the UML exactly.

You must NOT change the UML's existing class names, attributes, methods,
or relationships unless the student explicitly approves. If the rubric
requires something the UML does not already include, ADD it (one new
field, or one new method, or one new helper class) — do not redesign.

==========================================================================
STEP 1 — ASK THE STUDENT
==========================================================================
Ask only four short questions and wait for answers:
1. Provide the UML in ONE of these forms:
   - Path to a `.drawio` file in the project (e.g. `MySystem_UML.drawio`).
   - Path to an image (PNG/JPG/PDF) you can read.
   - A plain-text description of every class (name, attributes, methods)
     and every relationship (extends / implements / composition /
     aggregation, with multiplicities).
2. Project domain in one short sentence (e.g. "online food ordering").
3. Team names, IDs, and section number (for the report cover).
4. Any specific features the student wants (optional — leave blank to
   accept the AI's defaults).

==========================================================================
STEP 2 — PARSE AND PRINT THE UML BACK TO THE STUDENT
==========================================================================
After you have read the UML, list every class you see, in this format:

  - <ClassName> [interface | abstract | concrete | plain | composer | record]
      attributes:  <list>
      methods:     <list>
      relations:   <list of arrows in/out>

This step is verification only — the student will correct you if you
misread anything. Do NOT propose changes yet.

==========================================================================
STEP 3 — AUDIT AGAINST REQUIRED OOP COVERAGE
==========================================================================
For each rubric requirement, mark PASS / PARTIAL / MISSING:

  [ ] 1 interface with `public static final` constant + at least 1
      abstract method.
  [ ] 1 abstract parent class with at least 2 abstract methods (one
      numeric like `calcFee(int)` / `calcTotal(double)` and one void
      like `showFeatures()` / `showDetails()`).
  [ ] 2 or more concrete children extending the abstract, each with
      at least one unique attribute and overridden business methods.
  [ ] 1 plain class (typically the customer / member / user).
  [ ] 1 composer class that implements the interface AND composes the
      plain class with single-object composition (filled diamond,
      multiplicity 1).
  [ ] Composer has an auto-generated final ID using `Math.random`
      (range 1000–9999).
  [ ] Plain person/asset class has a Lab 1.2 style derived reference:
      `private final String <something>Ref`, set ONCE in the constructor
      via `generate<Something>Ref()` = first 2 chars of one String
      attribute + last 2 chars of the passed-in ID, concatenated and
      uppercased (e.g. fullName="Lamar Saud" + customerId="C-001"
      → customerRef="LA01"). This is in ADDITION to the passed-in ID.
  [ ] TWO classes implement the interface — the abstract parent AND
      the composer (interface polymorphism is a hard rubric rule).
  [ ] At least one concrete child has a UNIQUE public method that does
      not exist in the parent (used in Main via `instanceof` + downcast
      to demonstrate CH4).
  [ ] Static `count` counters in at least 2 classes.
  [ ] At least 1 REGULAR Java array (NOT `ArrayList`) somewhere in the
      model. The array's owner can be ANY class — abstract parent,
      plain class, composer, manager, or even a static array of
      constants. The only firm rule is: all array CRUD (grow / shrink
      / search / iterate) is performed in `Main`, never inside the
      class that owns the array.

Print the audit as a table the student can read at a glance.

==========================================================================
STEP 4 — PROPOSE MINIMAL ADDITIONS (PLAIN TEXT, WAIT FOR APPROVAL)
==========================================================================
For every MISSING or PARTIAL row in the audit, propose the SMALLEST
possible change. Examples:

- Missing 2nd abstract method → "Add `void showDetails()` to the
  abstract class. Each child overrides it with a one-line print."
- Missing unique method → "Add `boolean qualifiesForDiscount()` to one
  of the concrete children, used in Main via `instanceof` + downcast."
- Missing array → propose 2–3 placement options and let the student pick:
    * inside the plain class as a history of past activity (record
      class needed),
    * inside the abstract parent as a per-asset history (record class
      needed),
    * inside the manager as a fixed-size queue,
    * static `String[]` of domain constants (no new class) — this is
      the cheapest option but the weakest demo of array CRUD.
- Missing 2nd interface implementer → if the UML's composer does not
  implement the interface, propose adding `implements <Interface>` and
  one `calcXxx(...)` method to it.

Do NOT redesign. Each proposal should be one bullet describing one
addition. Wait for explicit student approval before producing any code.

==========================================================================
STEP 5 — BUILD ONE CLASS AT A TIME, PAUSING AFTER EACH
==========================================================================
Follow this file order (skip any class the UML already has and that
needs no change — but always show the final source so the student can
copy it):

1. The interface
2. The abstract class (if a record-class array lives inside it, add the
   `Record[]` field with getter/setter only — NO grow / shrink / search
   / iterate methods inside)
3. The concrete children (2 or more)
4. The plain class (if a record-class array lives inside this class,
   add the `Record[]` field with getter/setter only)
5. The composer (with `Math.random` ID, single-object composition of
   the plain class, and the interface-implementing `calcBill` /
   `calcTotal` / similar method)
6. The record class — ONLY if the UML or the audit step required it
7. The manager class (NOT in UML; two ArrayLists)
8. `WriteText.java` + `ReadText.java` (NOT in UML; teacher's utility
   style)
9. `Main.java` (NOT in UML; menu loop, validation helpers, and ALL
   array CRUD on whichever class owns the array)
10. `GUI.java` (NOT in UML; JavaFX with lambdas allowed only inside
    `setOnAction`)

After each class, show the full source and wait for "ok next".

STEP 6 — GENERATE Phase1_Report.md AT THE END
==========================================================================
Six sections: Project Overview, Class Descriptions (2–3 lines each),
UML Class Diagram (image placeholder pointing at the existing
`.drawio`), Relationships Summary, Input Validation, Work Distribution.
Student fills in team info in the header.

==========================================================================
RULES FOR DEALING WITH THE GIVEN UML
==========================================================================
- Treat every name in the UML as final — do NOT rename classes,
  attributes, or methods. If a UML method is named `calcCost`, the
  Java method is `calcCost`, not `calcBill` or `calcTotal`.
- Treat every multiplicity in the UML as final. If the UML shows
  `Customer 1 ◆──── 1..* Order`, write the code as Customer composing
  many Orders.
- The UML is the contract. The Java code matches the UML, not the
  other way around.
- Anything NOT in the UML (manager, Main, WriteText, ReadText, GUI,
  validation helpers) is a free addition — those classes never appear
  in any UML and never need student approval beyond the original
  high-level design.
- The regular Java array's location is whatever the UML shows (or
  whatever the student picked in Step 4 if the UML did not include
  one). The CRUD logic ALWAYS lives in `Main`, regardless of where the
  array field is declared.

==========================================================================
ALLOWED JAVA CONCEPTS (CH1–CH9 ONLY — strict)
==========================================================================
CH1: classes, private/public, getters/setters, `this`, constructor
     overloading, constructor chaining with `this(...)`, static fields
     + methods, `final` instance fields, String.format (`%d %s %.2f %b`
     `\n` `%n`), `Math.random()` with min/max ID formula, wrapper
     classes (Integer.parseInt, Double.parseDouble, Boolean.parseBoolean),
     ternary `? :`, String methods: trim, length, equalsIgnoreCase,
     toUpperCase, toLowerCase, contains, split(" "), startsWith,
     charAt(0), indexOf. (Prefer `length() == 0` over `isEmpty()`.)
CH2: composition (filled diamond), aggregation (empty diamond),
     has-a implemented as instance variable.
CH3: `extends`, `super(...)` first statement, `@Override` annotation.
CH4: ArrayList<Parent>, method overriding, `instanceof`, downcasting,
     dynamic dispatch through superclass references.
CH6: `abstract class`, `abstract method();` (no body), concrete
     subclasses must implement.
CH7: `interface` with `public static final` constant + `public abstract`
     method, `implements`, two different classes implementing the same
     interface. JavaFX basics ONLY inside the GUI class: GridPane,
     Label, TextField, Button, TextArea, Scene, Stage, `setOnAction(e -> { })`
     (lambda allowed HERE ONLY).
CH8: try/catch/finally, multiple catch (specific → generic), `throws`
     in method header (optional), `throw new IllegalArgumentException(...)`,
     `e.getMessage()`, exception propagation. Allowed built-in types:
     ArithmeticException, ArrayIndexOutOfBoundsException,
     NullPointerException, InputMismatchException, IOException,
     FileNotFoundException, IllegalArgumentException,
     NumberFormatException, NoSuchElementException,
     IllegalStateException, SecurityException, FormatterClosedException,
     ClassCastException, generic `Exception` (last-resort only).
CH9: `java.util.Formatter` for writing, `java.util.Scanner(new File(...))`
     for reading. Two dedicated utility classes WriteText + ReadText.

==========================================================================
FORBIDDEN — NEVER USE
==========================================================================
- Custom exception classes (anything `extends Exception`).
- Lambda expressions (except JavaFX event handlers inside GUI.java).
- Streams API.
- Collections other than ArrayList (no HashMap, TreeMap, LinkedList, etc.).
- try-with-resources.
- Multi-catch with `|`.
- Exception chaining `new Foo(e)`.
- `java.time.*` (LocalDate / LocalDateTime / etc.) AND `java.util.Date`
  AND any other non-CH1–CH9 API. If the project needs a date, choose
  ONE of:
    (a) ask the user for the date as a String input and validate it
        character-by-character with `readDate(...)`, OR
    (b) define a small CUSTOM `Date` class authored by the team in
        this exact shape:

```java
package <abbrev>;

// Custom Date value object — year/month/day with range validation.
public final class Date {

    private int year;
    private int month;
    private int day;

    // Parameterized constructor
    public Date(int year, int month, int day) {
        setYear(year);
        setMonth(month);
        setDay(day);
    }

    // Empty constructor
    public Date() {
        this(0, 0, 0);
    }

    public int getYear() { return year; }
    public void setYear(int year) {
        if (year < 2024) {
            System.out.println("invalid year");
        } else {
            this.year = year;
        }
    }

    public int getMonth() { return month; }
    public void setMonth(int month) {
        if (month < 1 || month > 12) {
            System.out.println("invalid month");
        } else {
            this.month = month;
        }
    }

    public int getDay() { return day; }
    public void setDay(int day) {
        if (day < 1 || day > 31) {
            System.out.println("Invalid day");
        } else {
            this.day = day;
        }
    }

    @Override
    public String toString() {
        return String.format("%d/%d/%d", getYear(), getMonth(), getDay());
    }
}
```

  Notes on this Date class:
    - Class is `public final` to prevent subclassing.
    - Field order is `year, month, day` (also the constructor order).
    - Setters use `System.out.println("invalid ...")` instead of
      throwing `IllegalArgumentException` — this is the only place in
      the project where validation is reported via println instead of
      exception. Match this pattern exactly when generating it.
    - `toString` is `YYYY/M/D` via `String.format("%d/%d/%d", ...)`
      (no zero-padding).
    - Year minimum is `2024` (project-domain choice; adjust per
      project if the student needs older dates).
    - Empty constructor passes `0, 0, 0` even though the setters will
      reject those — that mirrors the existing teacher style and keeps
      a no-arg default available.

  Use this Date as the type of any UML "date" field. In `Main`, build
  the Date by reading three ints (`readPositiveInt` is wrong for year/
  month/day because of the lower bounds — read raw ints and pass them
  to the Date constructor; the Date class itself handles range
  validation via its setters), or by reading a String and splitting
  on `/`.

  Never call `LocalDate.now()` / `LocalDateTime.now()` / `new java.util.Date()`.
- `@author`, `@version`, `{@inheritDoc}`, `{@link}`, `@see`, `@since`,
  `@throws` Javadoc tags.
- Records, sealed classes, `var`, generics beyond `ArrayList<Type>`,
  inner classes, reflection.
- Renaming classes, methods, attributes, or fields that already exist
  in the given UML.
- Adding fields, methods, or relationships that the UML does not
  contain — UNLESS the audit step flagged a missing requirement and
  the student approved the addition.

==========================================================================
STYLE PATTERNS (MANDATORY — identical for every class)
==========================================================================

--- Package ---
Use a short lowercase abbreviation of the project name (e.g. sps, fds,
etbs, fcbs, wis, dwms, trbs). Every `.java` file begins with
`package <abbrev>;`.

--- Constructor chaining ---
Default constructor calls full constructor with empty defaults:
    public ClassName() { this(0, "", 0.0, false); }
Full constructor:
  - assigns final ID directly (`this.SOMETHING_ID = id;`)
  - calls setters for every other field (so validation is reused)
  - increments static `count` if the class has one

--- Final ID field naming ---
UPPER_SNAKE_CASE (e.g., SPOT_ID, ORDER_ID, BOOKING_ID, WALLET_ID).
Getter method stays camelCase (`getSpotId()`, `getOrderId()`).

--- Math.random ID generation (only for the composer class) ---
    private int generateId() {
        int min = 1000;
        int max = 9999;
        return (int)(Math.random() * (max - min + 1)) + min;
    }
Called once inside the full constructor: `this.XXX_ID = generateId();`

--- Lab 1.2 derived reference (REQUIRED on the plain person/asset class) ---
Following the Lab 1.2 Employee/employeeRef pattern, the plain class (Customer,
Member, Owner, etc.) MUST also declare a `private final String <something>Ref`
field set ONCE inside the full constructor via a private
`generate<Something>Ref()` method. This is in ADDITION to the passed-in ID, not
a replacement. Generation rule:
  - First 2 characters of one descriptive String field already on the class
    (e.g. fullName, department, city — any String attribute the UML already has).
  - Last 2 characters of the entity's passed-in final ID (e.g. customerId,
    memberId, ownerId).
  - Concatenated with no spaces, stored in uppercase.

Example:
  fullName  = "Lamar Saud"
  customerId = "C-001"
  customerRef = "LA01"

Code template:
    private final String customerRef;

    // inside full constructor, AFTER the contributing fields are set,
    // BEFORE the static counter increment:
    this.customerRef = generateCustomerRef();

    public String getCustomerRef() { return customerRef; }

    /**
     * @return Lab 1.2 style derived reference: first 2 chars of fullName + last 2 chars of customerId, uppercase
     */
    private String generateCustomerRef() {
        String namePart = "";
        if (fullName != null && fullName.length() >= 2) {
            namePart = fullName.substring(0, 2);
        }
        String idPart = "";
        if (customerId != null && customerId.length() >= 2) {
            idPart = customerId.substring(customerId.length() - 2);
        }
        return (namePart + idPart).toUpperCase();
    }

Notes:
  - Show the ref in `toString()` as a separate line right after the ID line.
  - The empty constructor is allowed to produce an empty `""` ref because both
    contributing fields are empty defaults — the guards above handle that.
  - This pattern does NOT replace the composer's `Math.random` ID. The composer
    still uses `Math.random` for its primary ID; the plain class uses this
    derived-reference pattern in addition to its passed-in ID.
  - The substring slices use the same shape as Lab 1.2 (first 2 + last 2). Do
    not change to first 3 or last 3 — keep the lab pattern exact.

--- Static count pattern (at least 2 classes in the project) ---
    private static int count;
    // inside full constructor: count++;
    public static int getCount() { return count; }
    public static void setCount(int count) { ClassName.count = count; }

--- Setter validation style ---
NUMERIC setters that must be non-negative / positive:
    public void setX(double x) {
        if (x < 0) throw new IllegalArgumentException("X cannot be negative");
        this.x = x;
    }
STRING setters: no throw, just trim (and optionally toUpperCase or
toLowerCase where domain-appropriate):
    public void setName(String name) { this.name = name.trim(); }
BOOLEAN and OBJECT setters: direct assign, no validation.

--- toString pattern ---
    @Override
    public String toString() {
        return String.format("Field1: %d\nField2: %s\nField3: %.2f ...",
            getField1(), getField2(), getField3());
    }
Subclasses concatenate via `super.toString()`:
    return String.format("%s\nExtraField: %s", super.toString(), getExtra());

--- Menu pattern (Main.menu()) ---
Numbered options, period ending, 2-space indent for single-digit numbers,
final `>> ` prompt. Use `public static void menu()`:
    System.out.print(
        "\n1.  <Action 1>.\n"
      + "2.  <Action 2>.\n"
      + ...
      + "N.  Exit.\n"
      + ">> ");

--- Main entry point ---
Static fields at the top:
    public static <Manager> system = new <Manager>();
    public static Scanner input = new Scanner(System.in);
Main method: `fillList();` then welcome banner, then the do-while loop.
Helper methods take no parameters (they reference the static fields).
Outer loop structure:
    do {
        try {
            menu();
            choice = Integer.parseInt(input.nextLine().trim());
            switch (choice) { ... case N: System.out.println("Thank you!"); break; default: System.out.println("Invalid option!"); }
        } catch (InputMismatchException ex) { System.err.println("Invalid input"); input.nextLine(); }
        catch (NullPointerException ex)   { System.err.println(ex); }
        catch (ClassCastException ex)     { System.err.println(ex); }
        catch (ArrayIndexOutOfBoundsException ex) { System.err.println(ex); }
        catch (Exception ex)              { System.err.println(ex); }
    } while (choice != N);

--- Input reading ---
Never use nextInt() directly. Always:
    int x = Integer.parseInt(input.nextLine().trim());
    double y = Double.parseDouble(input.nextLine().trim());
Y/N confirmation:
    input.nextLine().trim().equalsIgnoreCase("Y")

--- Auto-link operations into one menu flow ---
If the project keeps a per-customer (or per-asset) history array, the
"create transaction" menu option (book a ride / place an order / open
a ticket / ...) MUST automatically grow that history array via a
private static `appendXxx(...)` helper. Do NOT expose a separate
"add to history" menu option — that is redundant and confusing. The
remaining three array operations (shrink / iterate / search) ARE
exposed as their own menu options so all four CRUD verbs are still
demonstrated.

--- fillList() sample data ---
Main.fillList() pre-populates the manager with 4–8 sample objects of
mixed types so the student can demo immediately. If the project has a
history array, also pre-seed 2–3 sample history entries so the
"display history" menu option shows real data on first run.

--- Manager class (e.g. "<Project>System" or "<Domain>Manager") ---
Has two ArrayLists (the abstract type and the composer type),
add/remove methods that take the OBJECT (not the id), findByXxxId
methods that return null if missing, displayAll and per-type display
methods that use `instanceof` filter, search method using
`toLowerCase().contains(...)`, optional calculateTotal method. Follows
Lab 7 Restaurant class style.

--- WriteText.java ---
    private Formatter output;
    openTextFile(String fileName) : try { new Formatter(fileName); }
        catch (SecurityException — separate catch)
        catch (FileNotFoundException — separate catch)
    writeToFile(<MainDomainObject> o) : try { output.format(o.toString() + "\n");
        output.format("\n---------------------------------------------\n"); }
        catch (FormatterClosedException)
    closeFile() : null-check then close.

--- ReadText.java ---
    private Scanner input;
    openTextFile(String) : try { new Scanner(new File(fileName)); }
        catch (FileNotFoundException)
    readFromFile() : try { while (input.hasNextLine()) accumulate; }
        catch (NoSuchElementException — print + System.exit(1) + input.close())
        catch (IllegalStateException — print only)
    closeFile() : null-check then close.
In Main, menu Save calls WriteText flow, Read calls ReadText flow.

--- GUI.java (JavaFX) ---
Extends Application. Simple GridPane with 1 title Label, 3–5 domain
TextFields with matching Labels, 2 Buttons (Add and Show), 1 TextArea
for output. Buttons use `setOnAction(e -> { ... })` — the ONLY place
lambdas are allowed. Read/write from `Main.<manager>` (which must be
static). Scene around 400x500. Style uses `setStyle("-fx-background-color: ...")`.
`main(String[] args) { launch(args); }` included for standalone run.
In Main, menu option calls `GUI.main(null);` inside try-catch.

--- Comments / Javadoc rules ---
Keep comments minimal and CS111 beginner level. Two formats only:

(1) Single-line `// ` comment for:
    - Class header (one short phrase, e.g. `// A taxi car.`)
    - Methods with NO @param or @return (e.g. `// Prints the menu.`,
      `// Fills the system with sample vehicles.`)
    - Default constructor: `// empty constructor` directly above the
      method (NO Javadoc block).
    - Override methods that do not introduce a new contract — one
      short line is enough.

(2) Javadoc `/** ... */` ONLY when the method has @param or @return:
    - Full constructor: short label "Full constructor" + one `@param`
      per argument.
    - Business methods that take parameters or return values
      (calcFee, calcTotal, calcBill, etc.): one-line description +
      `@param` + `@return`.

Rules:
- Getters and simple setters: NO comment at all.
- Allowed Javadoc tags: `@param`, `@return` only.
- Never use: `@author`, `@version`, `@see`, `@since`, `@throws`,
  `{@inheritDoc}`, `{@link}`.
- Don't repeat the obvious. If a method is named `displaySpots()`,
  "Displays all spots" adds no value; skip the comment.
- NO DEAD CODE — every method defined in the file MUST be called.
- DO NOT define a helper for a non-existent field.

--- Exception messages ---
Use short plain-English strings:
  "X cannot be negative", "X must be positive", "X must be at least 1".
All numeric validation errors are displayed in Main as:
  System.out.println("Error: " + e.getMessage());

--- UI separators (exact character counts) ---
  - Spot/item separator inside list displays: 42 dashes
  - Ticket/order separator: 42 equals
  - WriteText row separator: 45 dashes (between two newlines)
  - GUI TextArea separator inside Show handler: 18 dashes

--- Welcome / Exit messages ---
Welcome (printed once before the loop): `**** Welcome To <System Name> ****`
Exit: prints `Thank you!` on the Exit case, not on default.

==========================================================================
INPUT VALIDATION HELPERS (Phase 1 ALWAYS includes these)
==========================================================================

A bank of `private static` validation helpers is placed at the BOTTOM
of `Main.java`. Each helper prints its prompt, reads with
`input.nextLine().trim()`, walks the input character by character (no
regex, no streams), and re-prompts with a plain-English error message
on failure. ONLY define helpers that are actually called somewhere in
Main — no dead helpers.

Standard helpers (call only the ones the project needs):

| Helper | Rule |
|---|---|
| `readPositiveInt(String prompt)` | digits only, value > 0 |
| `readIntInRange(String prompt, int min, int max)` | digits only, value in [min, max] |
| `readPositiveDouble(String prompt)` | digits + at most one `.`, value > 0 |
| `readBoolean(String prompt)` | exactly `true` or `false` (case-insensitive) |
| `readName(String prompt)` | English letters and spaces only, length 2–50 |
| `readSaudiPhone(String prompt)` | exactly 10 digits, starts with `05` |
| `readPlate(String prompt)` | uppercase letters and digits only, length 6–8 |
| `readModel(String prompt)` | letters / digits / spaces, length 2–50 |
| `readLocation(String prompt)` | letters / digits / spaces, length 2–100 |
| `readDate(String prompt)` | DD/MM/YYYY shape, valid day-per-month, year in a sensible range (e.g., 2020–2030) |

For string-shape rules, write the bounds plainly. Pick numbers that
fit the domain, not generic ones.

If the existing UML field is a date:
  - If declared as `String` → use `readDate(...)` and store as String.
  - If declared as the team's CUSTOM `Date` class (the canonical
    `public final class Date { int year, month, day; ... }` shown in
    the FORBIDDEN section above) → keep that type. In Main, read
    three ints (year, month, day) using raw `Integer.parseInt(input
    .nextLine().trim())` calls — the Date class's own setters will
    print "invalid year/month/day" and reject the value internally —
    then pass them to `new Date(year, month, day)`.
  - If declared as `LocalDate` / `LocalDateTime` (java.time.*) or
    `java.util.Date` → ASK the student to switch the field to either
    `String` or to the team's custom `Date` class. The built-in date
    types are outside CH1–CH9.

## How the AI should use this template

1. Student pastes the `BEGIN PROMPT … END PROMPT` block into a fresh chat
   AND attaches (or links) the existing UML.
2. AI asks the 4 questions in Step 1.
3. AI parses and prints the UML back (Step 2) so the student can correct it.
4. AI audits the UML against the rubric (Step 3) and reports a PASS / PARTIAL
   / MISSING table.
5. AI proposes the smallest possible additions (Step 4) and waits for approval.
6. AI builds one class at a time (Step 5).
7. AI generates `Phase1_Report.md` (Step 6).
8. The student opens the existing `.drawio` in [diagrams.net](https://app.diagrams.net/),
   nudges anything that became visually crowded after the additions, and exports
   the PNG for the report.

## Quick sanity checklist (if the AI forgets)

Ask the AI to re-read these 9 rules before producing code:

- [ ] Package name matches the chosen domain's abbreviation.
- [ ] No UML class, attribute, or method was renamed.
- [ ] Abstract parent has at least 2 abstract methods.
- [ ] One concrete child has a unique method used via `instanceof` + cast.
- [ ] Two classes implement the interface (abstract parent + composer).
- [ ] One composer class has single-object composition of the plain class
      and an auto-generated `Math.random` ID.
- [ ] The plain person/asset class has a Lab 1.2 style derived reference
      (`private final String <something>Ref`, generated from first 2 chars
      of one String attribute + last 2 chars of the passed-in ID, uppercase).
- [ ] At least one regular Java array exists somewhere (per the UML or per
      the audit step), and ALL its CRUD logic lives in `Main`.
- [ ] The "create a transaction" menu option auto-grows the history array
      via a private helper — there is NO separate "add to history" option.
- [ ] WriteText + ReadText are separate utility classes (not methods on
      the manager), and JavaFX GUI uses lambdas only in `setOnAction`.
- [ ] Validation helpers at the bottom of Main are wired into every input
      site; no dead helpers; no `java.time.*` and no `java.util.Date`.
      Dates are either Strings (validated with `readDate`) or instances
      of a small CUSTOM `Date` class authored by the team.
